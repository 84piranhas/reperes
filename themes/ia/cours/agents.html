Un modèle de langage seul ne fait qu'écrire du texte. Un agent est un système où ce modèle, placé dans une boucle, choisit des actions, en observe le résultat et recommence jusqu'à atteindre un objectif. C'est ce qui fait passer de « réponds-moi » à « fais-le ». C'est aussi ce qui change la nature des risques : une erreur n'est plus une phrase fausse, mais une action exécutée.

La boucle

L'appel d'outils

Le mécanisme de base s'appelle l'appel d'outils (tool use, ou function calling). On décrit au modèle les outils disponibles : leur nom, ce qu'ils font, leurs arguments. Quand il juge utile d'en employer un, il n'exécute rien. Il écrit une demande structurée, en JSON (JavaScript Object Notation) : « appelle l'outil de recherche de commande avec le numéro 4521 ». C'est l'application qui exécute, puis renvoie le résultat au modèle.

Cette séparation est le point le plus important du chapitre. Un modèle n'a aucun pouvoir propre. Il a exactement ceux des outils qu'on lui branche. Toute la sécurité d'un agent se joue donc dans ce que ces outils permettent.

MCP, la prise standard

Brancher chaque outil sur chaque application demandait un développement à chaque fois. Un standard ouvert, lancé fin 2024, a changé cela : MCP (Model Context Protocol). Un serveur MCP expose des outils et des données, et toute application compatible peut s'y connecter. Les principaux fournisseurs l'ont adopté.

Un second protocole, A2A (Agent2Agent), vise la communication entre agents de systèmes différents. La distinction est simple : MCP relie un agent à ses outils, A2A relie des agents entre eux.

Le piège

Un serveur MCP est du code tiers auquel on donne la main sur ses données. En installer un trouvé sur Internet revient à installer un logiciel inconnu, avec en plus la capacité d'influencer le modèle par les descriptions d'outils qu'il lui présente. Il se choisit et se vérifie comme n'importe quelle dépendance.

La règle de conception est constante : la solution la plus simple qui marche. Beaucoup de besoins présentés comme des agents sont en réalité des workflows, où le modèle remplit une case à chaque étape. On ne passe à l'agent que lorsque le chemin ne peut pas être écrit d'avance.

Quelques architectures

  • L'enchaînement. La sortie d'un appel devient l'entrée du suivant.
  • Le routage. Un premier appel classe la demande et l'envoie vers le bon traitement.
  • L'orchestrateur et ses sous-agents. Un agent découpe la tâche et confie les morceaux à d'autres, chacun dans son propre contexte. C'est ce qu'on appelle un système multi-agents.
  • L'évaluateur. Un second appel relit le travail du premier et demande des corrections.

La mémoire

Le modèle n'a pas de mémoire propre. Sa mémoire de travail est sa fenêtre de contexte, qui se remplit à chaque étape : chaque résultat d'outil s'y ajoute. Sur une longue tâche, elle déborde. Deux remèdes : résumer régulièrement ce qui précède, et écrire l'essentiel à l'extérieur, dans des fichiers ou une base, pour le relire au besoin. Cette mémoire externe est aussi ce qui permet à un agent de reprendre un travail d'un jour à l'autre.

Pourquoi les agents échouent

  • Les erreurs se multiplient. Un agent juste à 95 % à chaque étape ne réussit une tâche de vingt étapes qu'un peu plus d'une fois sur trois. La fiabilité par étape doit être très haute pour que l'ensemble tienne.
  • Les boucles. L'agent répète la même action sans progresser.
  • Les coûts. Chaque tour renvoie tout le contexte. Une tâche d'agent consomme couramment dix à cent fois plus de tokens qu'une simple question.
  • Les actions irréversibles. Un courriel envoyé, un fichier supprimé, un paiement émis ne se rattrapent pas.
  • L'injection. Une page web ou un document lu par l'agent peut contenir des instructions qui le détournent. Le chapitre sur les risques y revient.

Les garde-fous

  • Le moindre privilège. Ne brancher que les outils nécessaires, avec les droits les plus étroits. Lecture seule tant que l'écriture n'est pas indispensable.
  • Le bac à sable (sandbox). Exécuter le code et les commandes dans un environnement isolé.
  • La validation humaine, ou HITL (Human-in-the-Loop). Toute action sensible ou irréversible attend l'accord d'une personne.
  • Les budgets. Un plafond de tours, de tokens, de durée et de dépense.
  • Les traces. Chaque décision, chaque appel d'outil et chaque résultat sont journalisés.
  • Une identité propre. L'agent agit avec son propre compte et ses propres droits, pas avec ceux d'un administrateur.

Le réflexe

Devant un projet d'agent, la question décisive n'est pas « que sait-il faire ? » mais « quelle est la pire action qu'il puisse exécuter, et qu'est-ce qui l'en empêche ? ».

À retenir

  • Un agent est un modèle dans une boucle : il choisit une action, observe le résultat, recommence.
  • Le modèle demande, l'application exécute. Il n'a que les pouvoirs des outils qu'on lui branche.
  • MCP standardise le branchement des outils. Un serveur MCP se vérifie comme toute dépendance.
  • Workflow quand le chemin est connu, agent quand il ne l'est pas. Toujours la solution la plus simple qui marche.
  • Les erreurs s'accumulent d'étape en étape. Moindre privilège, bac à sable, validation humaine, budgets et traces rendent un agent exploitable.
