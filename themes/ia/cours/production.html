Une démonstration convaincante se construit en deux jours. Un service fiable, surveillé, sécurisé et d'un coût maîtrisé demande des mois. Cet écart entre le prototype et la production est la première cause d'échec des projets d'intelligence artificielle (IA). Ce chapitre décrit ce qui le comble : des pratiques d'exploitation, des choix d'infrastructure et une discipline sur les coûts.

MLOps : exploiter du machine learning

Le MLOps (Machine Learning Operations) applique au machine learning les pratiques du DevOps (Development and Operations), qui rapprochent le développement et l'exploitation des logiciels. La différence tient en une phrase : un logiciel classique dépend de son code, un modèle dépend de son code et de ses données.

L'ensemble s'appuie sur une chaîne d'intégration et de déploiement continus, CI/CD (Continuous Integration / Continuous Delivery) : chaque changement est testé automatiquement avant d'atteindre la production.

LLMOps : exploiter une application à base de modèle de langage

Quand on utilise un modèle de langage sans l'entraîner, les objets à gérer changent. Le LLMOps (Large Language Model Operations) s'occupe de quatre choses.

  • Les prompts, versionnés et déployés comme du code.
  • Les évaluations, rejouées à chaque changement de prompt ou de modèle.
  • L'observabilité. Chaque requête laisse une trace : le prompt complet, les appels d'outils, la réponse, les tokens consommés, la durée, le coût. Sans ces traces, un incident ne s'explique pas.
  • Les garde-fous : filtrage des entrées et des sorties, limites, alertes.

Une API (Application Programming Interface) est l'interface par laquelle un programme en interroge un autre. La plupart des organisations combinent plusieurs options : un fournisseur pour les usages courants, un modèle hébergé en interne pour les données les plus sensibles.

Le matériel, en trois notions

  • Le processeur graphique, ou GPU (Graphics Processing Unit). C'est lui qui calcule. Un constructeur, NVIDIA, domine très largement ce marché. D'autres puces spécialisées existent, comme les TPU (Tensor Processing Units) de Google.
  • La mémoire du GPU, ou VRAM (Video Random Access Memory). C'est la contrainte principale : le modèle doit y tenir tout entier. Un modèle de 7 milliards de paramètres pèse environ 14 gigaoctets en précision normale et 4 à 5 une fois quantifié sur 4 bits. Un modèle de 70 milliards en demande dix fois plus.
  • Le serveur d'inférence. Le logiciel qui charge le modèle et répond aux requêtes. Son travail principal est de regrouper les requêtes simultanées pour les calculer ensemble, ce qui multiplie le débit.

Deux mesures de performance se tirent dessus : la latence, le temps de réponse à une requête, et le débit, le nombre de tokens produits par seconde pour l'ensemble des utilisateurs. Regrouper davantage de requêtes améliore le débit et dégrade la latence.

L'auto-hébergement ne devient rentable que si les machines travaillent la plus grande partie du temps. Un GPU allumé jour et nuit pour servir quelques requêtes par heure coûte bien plus cher qu'une API.

La discipline qui suit ces dépenses s'appelle le FinOps, contraction de Finance et Operations. Elle rattache chaque coût à un usage : par requête, par utilisateur, par tâche réussie.

Le piège

La facture surprise. Un prototype coûte quelques euros. Le même service ouvert à dix mille personnes, avec des agents qui enchaînent cinquante appels par tâche, peut coûter mille fois plus par utilisateur qu'un simple dialogue. Le coût se projette à l'échelle avant le lancement, et se plafonne par des budgets.

Tenir quand ça ne répond plus

Un service qui dépend d'un modèle hérite de ses pannes. Les fournisseurs imposent des limites de débit (rate limits), connaissent des incidents, et retirent leurs anciens modèles selon un calendrier annoncé. Trois parades sont devenues standard.

  • La passerelle IA (AI gateway, AI pour Artificial Intelligence). Un point d'entrée unique entre les applications et les modèles. Elle porte les clés d'accès, les quotas par équipe, la journalisation, le filtrage, et bascule sur un modèle de repli (fallback) quand le premier ne répond pas.
  • Les versions épinglées. L'application appelle une version précise d'un modèle, pas « la dernière ». Le changement de version est alors une décision, précédée d'une évaluation.
  • Le mode dégradé. Ce que fait le service quand le modèle est indisponible doit être prévu, et non découvert.

Où vont les données

Tout ce qui figure dans un prompt part chez celui qui fait tourner le modèle. Quatre questions se posent donc à tout fournisseur. Les données servent-elles à entraîner ses modèles ? Combien de temps sont-elles conservées ? Dans quelle région sont-elles traitées ? Qui peut y accéder chez lui ? Les offres professionnelles apportent des engagements contractuels sur ces points. Les versions gratuites grand public, souvent non.

À retenir

  • L'écart entre démonstration et production est la première cause d'échec. Il se comble par des pratiques d'exploitation.
  • MLOps pour les modèles que l'on entraîne, LLMOps pour les applications bâties sur un modèle de langage : versionner, évaluer, tracer.
  • API, cloud, auto-hébergement ou poste : le choix dépend des données, du volume et des compétences.
  • La mémoire du GPU décide de ce qui peut tourner. L'auto-hébergement ne se rentabilise qu'à forte utilisation.
  • Une passerelle, des versions épinglées, un mode dégradé, et des engagements écrits sur le sort des données.
